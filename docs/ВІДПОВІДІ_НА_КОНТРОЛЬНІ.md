# Відповіді на контрольні запитання

## 1. Переваги розподіленої СКВ Git порівняно з централізованими

У централізованих системах (SVN, CVS) історія зберігається лише на сервері, а в Git кожен
розробник має повну копію репозиторію з усією історією. Звідси переваги:

- **надійність** — втрата сервера не знищує проєкт, його можна відновити з будь-якої копії;
- **робота офлайн** — коміти, перегляд історії, створення гілок не потребують мережі;
- **швидкість** — більшість операцій локальні;
- **дешеве гілкування** — гілка в Git це лише вказівник на коміт, тому створюється миттєво;
- **цілісність** — кожен об'єкт ідентифікується SHA-хешем, непомітно змінити історію неможливо;
- **гнучкість workflow** — можна будувати різні моделі співпраці (fork, PR, кілька remote).

## 2. Як організувати ефективний Git workflow для команди

1. Обрати модель, відповідну до проєкту: для невеликої команди — Feature Branch Workflow / GitHub Flow.
2. `main` завжди стабільна; захистити її правилом (зміни тільки через PR з approve).
3. Кожне завдання — Issue; кожна функція — коротка гілка `feature/...` від актуальної `main`.
4. Узгодити конвенції: назви гілок, Conventional Commits, мова повідомлень.
5. Зливати через Pull Request з code review та (бажано) автоматичними тестами в GitHub Actions.
6. Після злиття видаляти гілки, регулярно оновлювати локальну `main`.
7. Позначати стабільні стани тегами й випускати релізи з CHANGELOG.

## 3. Кроки вирішення конфлікту при злитті

1. `git fetch origin` та `git merge origin/main` у своїй гілці → Git повідомляє про конфлікт.
2. `git status` — переглянути файли зі статусом *both modified*.
3. Відкрити файл, знайти блоки між `<<<<<<<`, `=======`, `>>>>>>>`.
4. Вирішити: залишити один варіант, інший або поєднати обидва.
5. Видалити всі службові маркери, зберегти файл, перевірити, що код працює (тести).
6. `git add <файл>` → `git commit` → `git push`.
7. Якщо щось пішло не так — `git merge --abort` повертає стан до злиття.

## 4. Як Pull Request допомагає підтримувати якість коду

- **Code review** — щонайменше одна людина перевіряє зміни до потрапляння в `main`, знаходить помилки й неочевидні рішення;
- **обговорення** — коментарі прив'язані до конкретних рядків, рішення документуються;
- **автоматичні перевірки** — CI (GitHub Actions) запускає тести та лінтери, PR з помилками не зливається;
- **захист main** — правила гілки забороняють пряме відправлення змін;
- **відстежуваність** — PR пов'язаний з Issue (`Closes #N`), видно, навіщо і ким зроблено зміну;
- **обмін знаннями** — уся команда бачить і розуміє код колег.

## 5. Стратегії запобігання конфліктам

- короткоживучі гілки й невеликі PR, часте злиття;
- регулярно підтягувати `main` у свою гілку (`git fetch` + `git merge origin/main`);
- розподіляти завдання так, щоб учасники працювали з різними файлами/модулями (як у нашому проєкті);
- модульна архітектура, невеликі файли;
- узгоджений стиль коду й автоформатування (black, prettier) — менше «шумних» змін;
- комунікація в команді: попереджати, якщо змінюєш спільний файл;
- не комітити згенеровані файли (`.gitignore`).

## 6. Як правильно вирішувати merge-конфлікти та якими інструментами

Правильно — **розуміти зміст обох версій**, а не механічно обирати «свою». Якщо незрозуміло,
навіщо колега змінив рядок — поговорити з ним. Після вирішення обов'язково запустити тести.

Інструменти:
- **командний рядок**: `git status`, `git diff`, `git merge --abort`, `git log --merge`,
  `git checkout --ours/--theirs <файл>` (узяти повністю одну версію);
- **VS Code**: підсвічування конфліктів, кнопки *Accept Current / Incoming / Both*, 3-панельний Merge Editor;
- **GitHub**: кнопка *Resolve conflicts* у PR для простих текстових конфліктів;
- **GitLens**, GitHub Desktop, `git mergetool` (meld, kdiff3), IDE від JetBrains.
